# AI評価

AI Insights（Phase 5）の回答品質を検証する方法を定義します。

> **実装状況**: 未実装（Phase 5）。この文書は評価設計です。Phase 1 では、評価に必要な記録先として `ai_analysis_logs` テーブル（質問・呼び出したツール・構造化回答・モデル・トークン数）のみ用意しています。

## アーキテクチャ上の前提

- **数値はSQL/Pythonの分析ツールが計算し、LLMは解釈・説明・提案を担当する**。
- LLMが呼べるのは、引数を検証済みの読み取り専用関数だけ（例: `get_funnel(period, channel)`）。生のSQLは生成・実行させない。
- 回答は構造化出力（JSON Schema）で、次の7項目を必須にする。
  1. 結論 2. 対象期間 3. 根拠となるデータ 4. 分析結果 5. 考えられる要因 6. 推奨アクション 7. 不確実性・分析の限界
- 「事実」（ツールの結果）と「仮説」（LLMの解釈）を別フィールドに分ける。

## 評価項目

| 項目 | 何を確かめるか | 自動評価の方法 |
|---|---|---|
| 数値の正確性 | 回答中の数値がツール結果と一致するか | 回答から数値を抽出し、ツール出力と照合（許容誤差は丸めのみ） |
| データ参照の正確性 | 質問に必要なツールを呼んだか | 期待されるツール呼び出し（名前・引数）と比較 |
| 対象期間の正確性 | 「先月」などを正しい日付範囲に変換したか | 固定日時で実行し、引数の期間を比較 |
| 根拠と主張の整合性 | 結論が根拠データから導けるか | ルール（例: 差がない/データ不足なのに「〜が良い」と断定していない）+ LLM判定の併用 |
| 不確実性の説明 | n・欠損・相関と因果の区別に触れているか | `sample_size_level` が anecdotal 以下なら限界の記載を必須とする |
| 提案の実行可能性 | 具体的な行動になっているか | 人手評価（5段階）。必要に応じてLLM判定 |

## テストセット（予定）

- 固定のテスト用データセット（実データではない、ラベル付きの検証用データ）を作成し、期待される数値を事前に計算しておく。
- 質問例（仕様より）: 「InstagramとTikTokのどちらが集客につながっている？」「先月の経営状況をまとめて」など。
- **データ不足ケース**を必ず含める（例: 投稿3件しかない状態で「どのテーマを増やすべき？」→ 断定せず、不足を説明できるか）。
- **追跡できない貢献**のケース（自己申告のみの紐づけで「この投稿が入会につながった」と断定しないか）。
- 評価は Vitest または pytest から実行し、結果をCIで記録する。

## 安全性

- AIに渡すのは集計結果のみ。個人情報（連絡先・生徒の呼び名）は渡さない。
- OpenAI APIキーは Edge Function の Secrets に保存し、ブラウザには出さない。
- `ai_analysis_logs` には個人情報を含めず、更新・削除を禁止して監査証跡にする。
