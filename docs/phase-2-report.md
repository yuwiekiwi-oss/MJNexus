## 2. 採用した技術と理由

- **SQLビューで率を計算**（`social_post_snapshot_kpis`）: 計算式が一か所になり、SQLのテストで検証できる。画面は計算し直さない。
- **RPC関数 `record_post_metrics`**: スナップショットと指標値を1トランザクションで保存し、途中で失敗したら全体を取り消す（中途半端な記録を残さない）。呼び出したユーザーの権限（RLS）で動く。
- **KPIカタログ（JSON）**: TypeScript・Python・テストが同じ計算式の定義を読む。SQLビューに対応する列が実在するかもテストで確認。
- **Recharts**: 成長推移（折れ線）とグループ比較（横棒）。色は色覚多様性に配慮した組み合わせを検証済み。
- **ネイティブの `<select>`**: スマホで入力しやすく、テストもしやすい。

## 3. データの処理方法

```
入力フォーム / CSV
   │  検証（zod・CSVパーサー）: 空欄=未記録、「未取得」「非対応」、0以上の整数
   ▼
record_post_metrics()  … 1トランザクション、RLSで権限確認
   ▼
social_post_metrics（記録時点） + social_post_metric_values（指標 × 状態 × 値）
   ▼
social_post_snapshot_kpis（記録時点ごとに横持ち + 率の計算）
   ▼
social_post_kpis（投稿 × 最新の記録時点）
   ▼
画面: グループ分け → 中央値・件数・信頼度（src/features/social/dashboard-model.ts）
```

- 率は **同じ記録時点の値どうし** で計算します。
- 率の分子・分母のどれかが実測でなければ「計算不能」とし、0%にしません。
- グループ比較では計算不能の投稿を除外し、「計算できた投稿数 / 全投稿数」を表示します。

## 4. 指標の意味と計算式（SNS指標）

| 指標 | 計算式 | 意味 |
|---|---|---|
| エンゲージメント率（リーチ基準） | (いいね + コメント + 保存 + シェア) ÷ リーチ | 届いた人のうち反応した割合 |
| エンゲージメント率（再生基準） | 同上 ÷ 再生数 | TikTokの補助指標 |
| 保存率 | 保存 ÷ リーチ | 「後で見返したい」価値 |
| シェア率 | シェア ÷ リーチ | 人に教えたい価値 |
| プロフィール遷移率 | プロフィールアクセス ÷ リーチ | 集客ファネルの入口 |
| リンククリック率 | リンククリック ÷ プロフィールアクセス | プロフィールからの行動 |
| 制作効率 | リーチ ÷ 制作時間（時間） | 1時間の制作で何人に届いたか |

これらは **SNS指標** で、問い合わせや入会への効果を示すものではありません。経営指標との違いは [decision-support-design.md](decision-support-design.md) にまとめています。

主なテスト内容:

- **DB**: 率の計算（24時間後の ER = 60 ÷ 800 = 7.5% など）、未取得を含むと計算不能、非対応のリンククリック率は NULL、不正な指標が1つでもあれば全体が保存されない、未来日時・空の記録を拒否、閲覧者・他組織は記録できない、追跡コードの一意性、施策・AI提案の権限、評価済みの施策は評価結果が必須。
- **画面**: 実績フォームが値・実測0・未取得・非対応を区別して送信する、空のフォームは送信しない、閲覧者には記録ボタンを出さない、公開済みで公開日時なしは保存しない、ダッシュボードが「SNS指標」と「未検証」を表示する、カンバンのステータス移動。
- **CSV**: クォート・改行・BOM、未登録URL・日時不正・公開前・未来・負数・重複の行を行番号付きで検出、エクスポートの式インジェクション対策と再取り込み。
